## 3. 구현 순서와 완료 기준

### A. 음성 설정 실패를 작은 독립 검사로 분리

1. 한 번 읽은 snapshot을 검사와 진단 기록에 함께 사용한다. 로그 기록용 재조회로
   실패 당시 값이 바뀌지 않게 한다. 준비 당시 기대값은 그대로 보존한다.
2. JSON 전체 문자열 대신 정확한 항목 집합·중복 여부·형식·실제 값을 비교한다.
   객체 property 순서는 의미로 취급하지 않는다. Binary는 유효한 base64를 검증하고
   원래 byte로 비교한다. String은 ordinal exact 비교하며 대소문자/공백/종료 byte를
   임의 정규화하지 않는다. 결손·추가·중복 항목과 지원하지 않는 형식은 거절한다.
3. 실패 기록에 controlled 항목 역할, 결손/형식/값/직렬화 차이 구분, 기대/현재 값의
   길이와 비가역 digest, 항목별 equality, shell 버전/bitness/elevation, SID 일치 여부,
   명시적 registry view와 비교 stage를 남긴다. 실제 값과 SID 원문은 남기지 않는다.
4. 정확한 읽기와 같은 snapshot의 구/신 비교 결과를 테스트 진단에서 함께 남긴다.
   구 비교만 실패하면 직렬화 원인, 항목 값도 다르면 실제 snapshot 불일치로 구분한다.
5. 사용자 실행 가능한 **음성 설정 전용 읽기 진단**을 제공한다. 게임·서버·CDB·시스템
   변경 및 전체 파일 해시를 수행하지 않는다. 현재 환경에서 재현되지 않으면 승인된
   짧은 관리자 진단을 수행하며 3분짜리 전체 실행을 원인 수집용으로 반복하지 않는다.

완료: property/항목 순서 변화는 통과, 실제 byte·형식·결손·추가·중복 변화는 거절하는
합성 행렬, logger가 검사에 사용한 snapshot을 그대로 기록하는 시험 통과.
실패 당시 실제 관측 증거 또는 동등한 환경 재현 없이 실제 원인을 확정했다고 하지 않는다.

### B. 테스트용 정밀 검사의 순서와 상태 표시 정비

1. 신뢰할 작은 entry/helper/계획 결박 → 소유자/권한/중복 실행/미완료 원복 확인 →
   음성·hosts·port·필수 서비스/드라이버 상태 등 빠른 조건 → 전체 파일/저장소 정밀 검사
   → 변경 직전 공유 상태 재확인 순서로 구성한다.
2. 사전 검사 앞쪽 통과만으로 변경을 허용하지 않는다. 긴 검사 중 상태가 변했는지
   변경 직전에 재확인한다. 필수 무결성·격리·소유권 검사를 제거하지 않는다.
3. 구간별 시작/끝·경과 시간·계획된 읽기 bytes/완료 bytes를 기록한다. 실제 측정한 값과
   예상 총량을 구분한다. UI에서 승인 대기/빠른 검사/정밀 검사/게임 시작/실행/원복을
   구분하고, 부모 프로세스가 존재한다는 이유만으로 게임 실행 중이라고 표시하지 않는다.

완료: 음성 불일치/포트 충돌 등 합성 조기 실패 시 대용량 reader 호출 0회,
게임/UAC 자동 호출 0회, 중도 변경 거절, 정밀 검사 보존과 UI 상태 전이 시험 통과.
현재 사용자 검증은 계속 정밀 경로를 사용해도 된다.

### C. 실제 사용용 빠른 경로 — 별도 계약으로 설계·검증

목표는 **UAC 승인 뒤 에이전트가 소유한 사전 검사와 준비로 추가하는 대기 p95 ≤ 5초**다.
UAC 사용자 응답과 원본 게임 자체의 로딩은 따로 측정한다. 서버/부트스트랩 단계의 검사
비용을 게임 로딩으로 숨기지 않는다. 목표값이지 현재 달성 수치가 아니다.

- 정밀/빠른 모드는 명시적으로 구분한다. 정밀 검사는 테스트·최초 준비·입력 업데이트·
  정밀 재검증에서 수행한다. 빠른 경로는 준비 완료 receipt만 있다고 허용하지 않는다.
- 준비된 세대에 build/profile/약점/manifest, physical-file identity, 내용 digest,
  변경 추적 기준점과 소유권 정책을 결박한다. 실행 시 작은 핵심 입력과 공유 상태를
  검증하고 **준비 이후 변경이 없다는 근거**를 확인한다.
- mtime/길이, 경로, 과거 성공 flag만으로 내용 무결성을 대신하지 않는다. 같은 길이
  변조·시간 복원·파일 교체·reparse/hardlink·원복 중단을 검출해야 한다. 변경 이력 공백,
  신원 불명, crash, 재시작 뒤 추적 연속성 결손은 준비 무효화로 처리한다.
- 변경 감지와 쓰기 통제가 원본 client의 합법적인 cache 쓰기와 공존하는지를 먼저
  제한된 합성 prototype에서 증명한다. 구체 수단은 이 결과로 확정하며, 보안 계약의
  변경 검토 없이 현재 whole-file hash 검사를 캐시된 boolean으로 대체하지 않는다.
- 무효화 시 `정밀 재검증 필요`를 즉시 표시하고 별도 준비 작업으로 안내한다.
  빠른 시작 버튼 뒤에서 3분 검사를 조용히 실행하거나 검사를 생략하고 시작하지 않는다.
- 부모 → store → bootstrap이 **같은 실행의 검증 결과와 신원/lease를 안전하게 인계**하도록
  바꾼다. 프로세스 경계에서 검증 결과를 신뢰할 근거가 없으면 재사용하지 않는다.
- CDB는 변경 범위가 작아도 현재 전체 읽기가 반복된다. 동일 exclusive handle을 유지한
  한 transaction 내 중복 Prepare부터 제거할 수 있는지 검증한다. 매 실행의 전체 CDB
  검사를 줄이는 것은 별도 generation/변경 추적/범위 검증 계약이 성립한 뒤에만 진행한다.
  외부 변경과 부분 쓰기 복구 검사를 삭제하지 않는다.
- 음성 값을 강제해야 하는 실제 이유를 별도 확인한다. 변경이 필요 없는 실행에는 음성
  변경/복원 자체를 제거하는 것을 우선 검토한다. 필요하면 실행별 원복 snapshot을
  새 계획에 결박한다. 기존 준비 snapshot을 덮어써 실패를 통과시키지 않는다.

접근 재검토 기준: 작은 prototype에서 변경 검출·빠른 재사용·안전한 복구 중 하나라도
성립하지 않거나 반복 해시를 다음 프로세스로 옮기는 데 그치면, 추가 전체 client 복제나
반복 실게임 대신 문제·대안을 먼저 보고한다. 30분간 같은 장애에서 진전이 없으면 방식 검토.
정밀 경로는 유지하고 빠른 경로를 완료했다고 표시하지 않는다.

### D. 회귀·설치·인수

1. 합성: 설정 비교, identity/내용 변경, 동일 크기 변조, journal/추적 결손, 중복 실행,
   process restart, 중도 쓰기/원복 실패, 상태/UI 전이, 거짓 ready/성공 승격 거절.
2. 무게임 성능: 준비 유효/무효와 정상/실패 경로를 cold-process/warm-process 각각
   20회 측정한다. OS 디스크 cache cold라고 부르지 않는다. 단계별 p50/p95/max와
   읽기 bytes, 부모뿐 아니라 store/bootstrap까지의 총 대기를 보고한다.
3. 회귀: repository/Phase 0/2A1/2A2/2B/3A/3B0/3B1/3B2/Actions 계약을 유지한다.
   DB/실행 영속 상태를 변경하면 격리 PostgreSQL integration도 다시 수행한다.
4. 설치: 봉인 controller/parent/bootstrap/entry/delivery의 hash 연쇄를 새 버전으로
   다시 준비하고 검증한다. 이미 사용한 entry/실패 evidence를 수정하지 않는다.
   필요한 새 assessment는 작은 실행 구성만 발급하고 기존 client 하나를 재사용한다.
   구버전 UI action의 hash를 새 실행에 섞거나 이전 실패 증거를 지우지 않는다.
5. 사용자: 필요 시 먼저 짧은 관리자 음성 진단, 이후 S29 정밀 테스트 1회.
   빠른 경로는 별도 성능/안전 계약을 통과한 뒤 사용자 게임 시작·종료로 인수한다.
   S26 재검증을 요구하지 않는다. 사용자 실게임은 자동 검사로 대체하지 않는다.

이전 실패의 원인을 확정하지 않는다. 근거는 Git 제외
`artifacts/validation-preflight-20260914/user-diagnostic-1/`에 있다.

C의 제한된 NTFS prototype은 같은 길이 변경+mtime 복원, 다른 파일로 교체, 하드링크를
거절했다. writable mapping이 남은 파일의 exclusive lease도 거절했다. journal ID/범위,
file USN/물리 identity, boot identity 변화의 무효화는 합성 단위 행렬에 포함한다.
실제 journal 설정이나 재부팅을 수행한 시험은 아니다.

측정 범위는 준비 hash 이후의 단일 합성 파일 재검증 함수다. Verify의 내용 읽기는 0이며
메타데이터 조회 비용은 시간에 포함한다. 프로세스 시작/준비 hash/실제 client/store/bootstrap
총 대기는 포함하지 않는다. cold-process는 각기 새 프로세스이며 OS disk cache cold가 아니다.
근거는 `generation-benchmark-1/summary.json` 및 각 20개 sample receipt다.

남은 핵심은 검증 시점의 lease를 실제 소비 시점까지 안전하게 전달하는 계약이다.
현재 prototype은 함수 반환 시 lease를 닫으므로 이후 변경을 막지 못한다. 캐시된 receipt를
실제 실행 permit으로 사용하지 않으며 production launcher에서 이 prototype을 호출하지 않는다.
다음 검증은 같은 실행에서 유지한 handle/소유권 인계, CDB의 승인된 범위 쓰기 후 세대 전환,
중간 crash와 복구 실패 시 세대 폐기다. 증명 전에는 전체 hash를 제거하지 않는다.
