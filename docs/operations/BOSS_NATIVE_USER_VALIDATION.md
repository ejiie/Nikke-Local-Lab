# 신규 보스·보정 FX 사용자 실게임 검증

2026-09-13 담당 범위: 게임 실행·화면/전투 판정은 운영자, 구현·오프라인/자동 검사·
검증용 배포·복구 도구·CI/병합은 에이전트가 맡는다. **기존 151/S26 인수는 완료**이며
이 문서는 기존 S26을 처음부터 다시 검증하라는 요청이 아니다.

## 실행 전 인계 조건

시즌 UI와 승인된 보스 사진은 설치됐으므로 다음 관리도구 실행에서 볼 수 있다.
단, **S29 검증용 게임 실행 구성은 아직 준비 완료가 아니다.** 미처리 카드의 가져오기는
오프라인 조립까지만 진행하며 native 전달 대기 상태를 완료로 바꾸지 않는다.
운영자는 ACE-ADVT의 사용자 실행 중 자동 시작/종료 후 정상 중지를 추가 승인했다.
이 승인을 반영한 helper의 합성 검증과 실제 실행기 연결·사용자 실게임은 별개다.

현재 보정 FX는 오프라인 후보다. 아래 조건을 갖춘 **새 검증용 실행 구성을 인계받은 뒤**
검증한다. `artifacts`의 CDB·bundle을 공식 설치본이나 운영 캐시에 수동 덮어쓰지 않는다.

- 선택 시즌·보스·기본 약점과 이번 실행 약점이 표시되는 준비 상태
- 검증된 v6/운영 DB/공유 캐시와 분리된 실행 대상 및 변경 파일 hash/원복 기준
- 관리자 실행을 유지하면서 프로세스 Job과 승인된 ACE 서비스 범위를 관리하는 실행기
- 필요한 드라이버 전환의 별도 승인 및 종료 시 정상 원복 절차
- 시작 실패/중도 종료/재시도 상태와 원복 결과를 확인할 수 있는 경로

이 조건이 미비하면 아직 사용자 테스트를 요청할 수 있는 상태가 아니다. 오프라인
`offline_*_verified` receipt, HTTP 응답 성공, 로비 접속만으로 조건을 충족했다고 표시하지 않는다.

## 사용자가 확인할 항목

| 구분 | 확인할 내용 | 성공 판단 |
| --- | --- | --- |
| 시즌 선택 | 같은 보스의 다른 시즌이 별개이며 선택 시즌으로 Challenge 진입 | 화면 시즌·보스·패턴이 선택한 시즌과 일치 |
| 기존 원본 FX 기준 | 새 격리 실행 구성에서 보정 전 상태 관찰 | 기준 화면을 기록하며 보정 수락으로 처리하지 않음 |
| 보정 FX | 보정 대상 쉴드의 생성·유지·파괴 시점 | 보스에 맞는 위치/크기, 잘림·치우침·과도한 확대 없음 |
| 5약점 | 작열·수냉·풍압·전격·철갑을 실행 전에 각각 선택 | 선택 약점 표시와 실제 공격 유효성 일치 |
| 속성 실드 | 같은 속성과 다른 속성 공격을 비교 | 시즌 원래 실드 규칙을 유지하면서 선택 속성에 맞게 작동 |
| S29 패턴·QTE | 소환·부위·페이즈 전환 및 속성 QTE | 누락·멈춤 없이 진행, QTE 허용 속성과 표시 일치 |
| 결과·재실행 | 중도 종료와 정상 결과창 종료 후 다시 실행 | 진행/결과 보존과 새 실행 가능, 다른 시즌/속성에 보정 잔류 없음 |
| 원복 비교 | 기준 A → 보정 B → 원복 A | 처음 기준과 원복 후 화면 일치; 에이전트의 파일 hash 원복 검사와 별개 |

보스 **약점**과 보스 자체 **속성**은 다르다. 현재 변형 규칙은 다음과 같다.

| 선택 약점 | 보스 자체 속성 | 새 Transform 보정 대상 |
| --- | --- | --- |
| 작열 | 풍압 | 해당 |
| 수냉 | 작열 | 해당 |
| 풍압 | 철갑 | 해당 |
| 전격 | 수냉 | 기존 정확한 매핑 확인 |
| 철갑 | 전격 | 원본 기준 FX |

기본 약점 표시는 실행 약점 변경 후에도 해당 시즌 원본 값으로 유지해야 한다.
한 속성의 성공을 나머지 속성 성공으로 확대하지 않는다.

## 결과 전달

시즌·선택 약점·실패 시점(진입/실드 생성/실드 파괴/QTE/결과/종료)과 화면 증상을 알려준다.
가능하면 해당 순간 스크린샷을 첨부한다. 실제 계정 인증값·토큰이나 원본 리소스를
GitHub에 첨부하지 않는다. 재다운로드·무결성·관리자/서비스 경고가 뜨면 임의로 설치를
진행하거나 원본 캐시를 바꾸지 말고 그 화면을 먼저 전달한다.

자동 로그는 요청/파일/프로세스 관측 근거이며, 화면 정상·전투 정상 판정은 사용자
확인으로 별도 기록한다. 실패 실행 receipt는 원복 성공으로 덮어쓰지 않는다.
